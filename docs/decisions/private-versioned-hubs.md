# Private, Versioned, Reviewable Hubs — Personal State Outside the Checkout

- **Status:** Accepted
- **Date:** 2026-08-05
- **Related:** `docs/brainstorms/2026-08-04-private-versioned-hubs-requirements.md`, `docs/plans/2026-08-05-001-feat-private-versioned-hubs-plan.md`, `docs/decisions/knowledge-management.md`

## Context

`docs/decisions/knowledge-management.md` made hubs the assistant's source of truth ("hub wins when a hub and a brief disagree") but left them pure convention: a gitignored directory inside the checkout, holding a README and one scaffold, with zero code references anywhere in `scripts/`, `trust/`, `deploy/`, or the `Makefile`. Nothing versioned them, nothing pushed them off-box, and nothing let the owner see what an always-on assistant had written into them — the audit log records that a gate decision happened, never what the assistant concluded as a result.

Privacy here cannot be enforced by the mechanisms the rest of the system uses, and that is settled rather than newly discovered. `trust/config/connector-legs.toml` declares Bash a blind spot in its own words — *"Do NOT rely on the gate to stop Bash-based exfiltration"* — and git runs through Bash. The repo's real leak gate (gitleaks plus `scripts/publish_gate.py`) is installed by `make dev`, a developer target, and was verified absent from the running deployment: the machine where an autonomous agent holds ungated Bash is precisely the machine with no pre-commit hook. `.gitignore` is a convention, not a barrier. So the barrier has to be structural — personal state simply is not inside the public checkout — and whatever backstop exists has to run where deployments actually run, which is service start.

Hubs are the first instance of a general problem, so the layout is decided for personal state as a class rather than for hubs alone. That is deliberate: specifying the rule per artifact is how `.claude/settings.json` was missed once already.

## Decision

1. **Personal state is partitioned into three tiers, and each tier gets a different home.** *Public, tracked* — machinery, docs, and scaffolds; this checkout, and nothing else. *Private, versioned* — hubs, where history is the entire point; a private git repository outside the checkout. *Private, never versioned* — secrets and credentials, which carry the **opposite** requirement, because a secret committed once survives its own deletion and in a public repo is world-mirrored and un-publishable; those live at a path with no git repository anywhere above them (`~/.config/buzai/secrets/`, 0600). The public repo tracks only `.example` scaffolds for secret-bearing config, and real values under `deploy/env/*.env` consolidate onto the outside-the-repo location, leaving one rule instead of two.
2. **Hub content lives in a private git repo outside the checkout, at one resolved location.** `$BUZAI_HUBS_DIR`, defaulting to `~/hubs`. `scripts/hub_paths.py` is the only place that path is computed, and it refuses two shapes after symlink resolution: a path *inside* the checkout (the direct leak) and a path that *contains* the checkout (a hub repo `git init`ed above this one would swallow it). Resolving after symlinks is the point — a `~/hubs` symlink aimed back into the checkout is exactly what a lexical string comparison waves through. Every consumer prints what it resolved, so a misconfiguration shows up in the journal instead of quietly writing to the wrong store. The convention's carrier is the tracked, public-safe `CLAUDE.md`; the override belongs in the systemd unit, never a shell profile, because a `--user` unit sources neither `.profile` nor `.bashrc`.
3. **`make hub-init` instantiates the store; the owner creates the remote.** The verb creates and seeds the repo from the tracked scaffolds, writes the store's own README (carrying the restore procedure, so it travels inside the backup), records a committed `.buzai/remote-expected` marker, migrates any real hub content still sitting in the checkout out to the new repo, and commits — as two commits: a parentless seed of scaffolding, then a child commit holding whatever was migrated. Review excludes the parentless commit, so migrated content has to sit outside it to stay reviewable. It is idempotent and refuses to initialize over a non-empty non-repo directory. It then **stops** and prints the owner-run commands: creating the private repository is the single step where a wrong flag publishes the knowledge base, so it is never automated.
4. **Nothing is pushed to a remote that has not been proven private, and the proof is an anonymous readability probe.** `scripts/hub_remote.py` runs `git ls-remote` with every credential channel suppressed; a read that *succeeds* proves the repository is publicly readable and the push is refused. Public readability is exposed over https, never over ssh, so the https twin of an ssh remote is derived and probed too — an ssh-only probe is refused for a public repo just as loudly as for a private one, which would have made the check report "private" for a world-readable store. There are three verdicts and no permissive fallback: **public** refuses, **indeterminate** (unreachable, timeout, unrecognized error, no derivable endpoint) refuses and queues, and only **private** — every anonymous probe definitively refused *and* the authenticated probe succeeding — permits a push. A fourth, **local-only**, means no remote is configured and is a durability condition, pointedly not the same thing as public. The verdict is cached with a one-hour TTL inside the hub repo's git directory and re-verified at service start, on expiry, and on URL change, because visibility can flip to public through a web UI with the clone URL unchanged. The credential is an ssh deploy key scoped to the hub repo (`~/.ssh/buzai-hub`), never a token embedded in a remote URL — git echoes the remote on failure and the unit sends stderr to the journal. The preflight also asserts the **public** origin still has no credential helper: this work could break the assumption the whole barrier rests on, so it is checked rather than assumed.
5. **One operation becomes one reviewable commit, through a single writer.** `scripts/hub_commit.py` takes an *operation* — append-entry, replace-section, remove-entry — never pre-rendered file content, so the read happens inside the critical section. An exclusive `flock` spans read → modify → atomic write → credential scan → commit; the push runs **after** release, bounded by an explicit timeout, because git has no default network timeout and a blackholed connection inside the lock would block every write on the box. The scan looks for credential **shapes** only (private-key headers, known token prefixes, `Authorization:` values, secret-shaped assignments, high-entropy opaque strings) over the lines the operation added, and a match rolls the file back to its prior content: the commit is the durability boundary, so a refusal leaves nothing behind on disk either. Commits carry an `instruction-source` trailer (autonomous / owner-directed / owner-correction) and a distinct assistant author identity; content found already uncommitted in the hub worktree is committed as `unattributed` rather than left invisible to review or folded into the assistant's own commit. Push failure is never fatal — the commit stands, the sha goes into a backlog, and retry happens on the next write and via `make hub-push` at service start. Divergence **halts**: nothing is merged, rebased, or force-pushed.
6. **Review disposition is a git note, and review never shows a diff.** Dispositions live per commit under `refs/notes/buzai-review` — append-only, keyed by sha so concurrent sessions touch different blobs, and travelling with the repo on restore. `make hub-review` returns undisposed commits as their message text in plain language; the owner approves or rejects per item and anything not acted on stays pending, because there is no time window and no "last reviewed" marker to sweep past undecided items. A rejection carries the owner's reason and *optionally* a correct value: with a value the content is replaced, without one it is **removed** — never re-derived, because the writing session and its source material are gone and an invented correction is worse than the original error, since it carries the owner's approval. Corrections are recorded through the same write path as everything else. The summary leads with a warning when the oldest unpushed commit exceeds 24 hours, so a silent backlog surfaces on the one surface the owner looks at, with no scheduler or digest.
7. **The deployment-side backstop is the existing `ExecStartPre` preflight, split fatal from warning.** `scripts/secrets_preflight.py` is the one control that actually runs on deployments. **Fatal** (blocks start): personal hub content in the checkout's `hubs/`, a real `.env` under `deploy/env/`, a hub path inside or containing the checkout, a hub deploy key that is not 0600 or is tracked by any repo, a credential helper on the public origin, and the pre-existing secrets perms/tracked checks. **Warning** (never blocks start): a store older than a seven-day grace period with no remote, an unpushed backlog, a dirty hub worktree, a git repo nested above the hub directory. With `StartLimitBurst=5`, making a durability condition fatal would convert "knowledge is not backed up" into "the assistant is gone" — a trade this design refuses. Every check is fed paths that can actually fail, and legitimate empty states (no hub repo, scaffold-only `hubs/`, zero local secret files) pass cleanly.
8. **R13 restated honestly — an accepted, documented gap.** The origin document said this work requires no trust reclassification because hubs stay outbound-only. That is true as far as it goes and it is not the whole truth: **hub push is a new outbound flow of personal data to a third party.** It raises no gate leg only because Bash is a declared blind spot, so a test asserting "no external-send leg fires" would be tautological and would prove nothing. What R13 actually means is that no *gate-visible* classification changes. The outbound flow itself is an accepted gap, justified by the destination being verified-private before every push (decision 4) and by the credential being scoped to that one repository — **not** by any claim that no external send occurs. A GitHub private repo is also not end-to-end encrypted and the provider can read it; that is accepted for this content, and swapping to a self-hosted or encrypted remote later changes nothing else in this design.

## Consequences

- **Plus:** `git pull` can update the checkout with no possibility of trampling or publishing personal data, and a re-clone no longer destroys the knowledge base; losing the host costs at most the unpushed tail; the owner can answer "what did it write, and is it right?" from a phone with no new surface to host or log into; review outcomes are themselves in history, so a rejection leaves a trail; the same partition already covers secrets and will cover the deferred `.claude/` class without re-deriving it; the barrier holds on a deployment with no pre-commit hook and no gate coverage of Bash.
- **Minus:** more moving parts on the durability path — a lock, a backlog, a TTL cache, and a notes ref that git neither pushes nor fetches by default, so restore takes one documented extra command; the preflight is now load-bearing for availability, mitigated only by the fatal/warning split; the owner must create the private remote and its deploy key by hand, and until they do, history is local-only; a fine-grained token or deploy key expiring is an *expected* steady state rather than an edge case, so a silent backlog is a condition the system has to keep surfacing; divergence halts and needs a human; and the outbound flow in decision 8 is a real, unmapped gap the gate does not see.

## Non-MVP / Future

- **A browsable rendered surface** (site or wiki) for accumulated hub content — the owner's stated priority, deferred on timing rather than merit, pending evidence of whether they navigate or interrogate.
- **A pushed digest.** Review is pull-only this pass; a scheduled summary is additive and needs no change to the substrate.
- **Active notification of a stale push backlog** (email/push) beyond the warning the review summary and the preflight already print.
- **Template-drift reporting** — telling the owner that public scaffolds changed after their hub repo was instantiated.
- **Personal skills, agents, and commands under `.claude/`** — the same artifact class under R3, but their layout is a genuine open question because Claude Code loads them from fixed paths. A named follow-on brainstorm.
- **Versioning `trust/config/*.local.toml`** — a plausible member of the private-versioned tier, not required for this pass.
- **Adopter-facing packaging** of any of the above. Not decided; the choices here avoid foreclosing it.

## Alternatives considered (rejected for MVP)

- **Verifying the remote's visibility with `gh`:** the two halves are mutually exclusive. `gh auth login` installs a **global** `github.com` credential helper, which would hand this instance push access to the *public* buzai origin and destroy the assumption the whole barrier rests on; and the R4-compliant credential — a deploy key scoped to the hub repo — has no API access at all, so `gh repo view` could never succeed and a fail-closed rule would refuse every push forever. The anonymous readability probe is provider-agnostic, needs no new dependency, and adds no credential.
- **Rebasing or merging on divergence:** it would pull remote commits into files the assistant then reads back as trusted source of truth — a genuine inbound write path, contradicting R13 and letting a compromised remote or credential inject "approved" content. Force-pushing instead would discard the owner's own work. Halting and surfacing is the only option that does neither.
- **Encrypting hub content into the public repo** (git-crypt, age, transcrypt): ciphertext in a public repo is permanent and world-mirrored, so a later key compromise is retroactive and un-deletable, and encrypted blobs destroy the reviewable diffs and plain-language history that are the point of this work.
- **A JSON review-state file:** defective either way it is committed. Uncommitted, the audit trail dies with the host and a restore resurfaces every already-approved item as pending, so the owner re-reviews their whole history. Committed, two sessions attached to the same hub write conflicting versions of one file and the loser's dispositions vanish — or land as a conflict marker inside the record of what was approved. Per-commit notes have neither problem and push and restore with the repo.
- **`scripts/publish_gate.py` as the hub leak scanner:** wrong twice over. On the deployment its pattern file is absent, so it matches almost nothing; on the maintainer's workstation its private patterns match the very hostnames and handles a legitimate personal hub is *supposed* to contain, so it would refuse valid commits. The hub scanner detects credential shapes and explicitly does not apply public-repo PII patterns to private hub content.
- **`CLAUDE.local.md` or a cross-boundary `@~/...` import as the hub-path carrier:** the first is protected by gitignore alone, which R3 rules out; the second triggers an approval dialog a headless session cannot answer. The tracked, public-safe `CLAUDE.md` carries the convention because nothing the assistant needs to know about the layout is secret.
